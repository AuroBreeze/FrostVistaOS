# The Slab Allocator: An Object-Caching Kernel Memory Allocator

**作者：** Jeff Bonwick (Sun Microsystems)

**出处：** USENIX Summer 1994 Technical Conference

---

## 摘要 (Abstract)

本文全面概述了 SunOS 5.4 内核内存分配器的设计。该分配器基于一组**对象缓存原语（object-caching primitives）**，通过在对象多次使用之间保留其状态，从而降低了分配复杂对象的开销。这些原语在管理无状态内存（例如数据页和临时缓冲区）时同样高效，因为它们兼具极高的空间利用率和极快的处理速度。该分配器的对象缓存能够动态响应全局内存压力，并采用了一种对象着色（object coloring）方案，从而提升了系统的整体缓存利用率与总线平衡。此外，该分配器还具备多项统计与调试功能，能够检测出整个系统中范围广泛的各类问题。

---

## 1. 引言 (Introduction)

对象的分配与释放是内核中最常见的操作之一，因此一个高效的内核内存分配器至关重要。然而在许多情况下，初始化和销毁对象的开销甚至超过了为其分配和释放内存的开销。因此，尽管优化分配器本身大有裨益，但通过缓存常用对象以在多次使用之间保留其基本结构，所能获得的收益要巨大得多。

本文首先讨论对象缓存技术，因为该技术所需的接口将决定分配器其余部分的设计。下一节将详细介绍具体实现。第 4 节描述了缓冲区地址分布对系统整体缓存利用率和总线平衡的影响，并展示了一种简单的着色方案如何同时改善这两者。第 5 节将该分配器的性能与其他几种著名的内核内存分配器进行了对比，结果表明它在空间和时间效率上通常都更为出色。最后，第 6 节介绍了该分配器的调试功能，这些功能可以检测出系统中存在的各类问题。

## 2. 对象缓存 (Object Caching)

对象缓存是一种用于处理频繁分配和释放对象的技术。其核心思想是在多次使用之间保留对象初始状态中不发生变化的固有部分——即**已构造状态（constructed state）**，从而不必在每次使用对象时都重新销毁和创建它。例如，包含互斥锁（mutex）的对象只需在首次被分配时执行一次 `mutex_init()`；在此之后，该对象可以被反复释放和重新分配，而无需每次都承受 `mutex_destroy()` 和 `mutex_init()` 的巨大开销。对象中嵌入的锁、条件变量、引用计数、与其他对象关联的链表以及只读数据，通常都属于已构造状态。

缓存之所以重要，是因为构造对象的开销可能远高于为其分配内存的开销。例如，在运行 SunOS 5.4 开发版内核的 SPARCstation-2 上，本文介绍的分配器将分配和释放一个流头（stream head）的开销从 33 微秒降低到了 5.7 微秒。如下表所示，大部分开销的节省都归功于对象缓存：

| Allocator | Construction + Destruction | Memory Allocation | Other Init. | Total Cost (μsec) |
| --- | --- | --- | --- | --- |
| **Old** | 23.6 | 9.4 | 1.9 | 34.9 |
| **New** | 0.0 | 3.8 | 1.9 | 5.7 |

对象缓存在多线程环境中尤为有效，因为许多最频繁分配的对象都包含一个或多个嵌入锁、条件变量以及其他可构造的状态。

对象缓存的设计非常直观：

To allocate an object:

```text
if (there’s an object in the cache)
    take it (no construction required);
else {
    allocate memory;
    construct the object;
}

```

To free an object:

```text
return it to the cache (no destruction required);

```

To reclaim memory from the cache:

```text
take some objects from the cache;
destroy the objects;
free the underlying memory;

```

对象的已构造状态只需在其首次进入缓存时初始化一次。一旦缓存被填充完毕，对象的分配与释放就会变得极为快速且轻量。

### 2.1. 示例 (An Example)

考虑如下数据结构：

```c
struct foo {
kmutex_t foo_lock;
kcondvar_t foo_cv;
struct bar *foo_barlist;
int foo_refcnt;
};

```

假设在没有对 `foo` 结构的外部引用（`foo_refcnt == 0`）且其所有挂起的 `bar` 事件（不论具体是什么）都已完成（`foo_barlist == NULL`）之前，该结构不能被释放。动态分配的 `foo` 对象的生命周期大致如下：

```c
foo = kmem_alloc(sizeof (struct foo),
KM_SLEEP);
mutex_init(&foo->foo_lock, ...);
cv_init(&foo->foo_cv, ...);
foo->foo_refcnt = 0;
foo->foo_barlist = NULL;
use foo;
ASSERT(foo->foo_barlist == NULL);
ASSERT(foo->foo_refcnt == 0);
cv_destroy(&foo->foo_cv);
mutex_destroy(&foo->foo_lock);
kmem_free(foo);

```

请注意，在每次使用 `foo` 对象之间，我们执行的一连串操作本质上只不过是一个开销昂贵的空操作（no-op）。所有这些开销（即上述除了 ‘‘use foo’’ 之外的所有操作）都可以通过对象缓存来消除。

### 2.2. 在中央分配器中实现对象缓存的必要性 (The Case for Object Caching in the Central Allocator)

当然，对象缓存完全可以在不需要中央分配器任何协助的情况下实现——任何子系统都可以拥有上述算法的私有实现。然而，这种方法存在几个缺点：

(1) 想要保留内存的对象缓存与想要收回该内存的系统其余部分之间存在着天然的张力。私有管理缓存无法合理地协调这种张力。它们对系统整体的内存需求知之甚少，而对彼此的需求更是毫无所知。同样，系统的其余部分也不知道这些缓存的存在，因此无法从它们那里“抽回”内存。

(2) 由于私有缓存绕过了中央分配器，它们也绕过了该分配器可能具备的任何统计机制和调试功能。这使得操作系统更加难以进行监控和调试。

(3) 针对常见问题存在同一解决方案的多个实例，会增加内核代码体积和维护成本。

相比标准 `kmem_alloc(9F)/kmem_free(9F)` 接口所允许的方式，对象缓存需要分配器与客户（client）之间进行更高程度的协作。下一节将开发一个接口，用以支持中央分配器中的已构造对象缓存。

### 2.3. 对象缓存接口 (Object Cache Interface)

这里展示的接口基于以下两个观察结果：

(A) 对对象的描述（名称、大小、对齐方式、构造函数和析构函数）属于客户，而非中央分配器。分配器不应该只是“知道”例如 `sizeof (struct inode)` 是一个有用的缓冲池大小。这种假设是脆弱的 [Grunwald93A]，并且无法预见第三方设备驱动程序、流（streams）模块和文件系统的需求。

(B) 内存管理策略属于中央分配器，而非其客户。客户只需要快速地分配和释放对象，而不必担心如何高效地管理底层内存。

由 (A) 可知，对象缓存的创建必须由客户驱动，并且必须包含对象的完整规范：

(1)

```c
struct kmem_cache *kmem_cache_create(
char *name,
size_t size,
int align,
void (*constructor)(void *, size_t),
void (*destructor)(void *, size_t));

```

创建一个对象缓存，每个对象的大小为 `size`，并按照 `align` 边界对齐。对齐参数总是向上取整到允许的最小值，因此当不需要特殊对齐时，`align` 可以为零。`name` 用于在统计和调试中识别该缓存。`constructor` 是一个用于构造（即执行一次性初始化）缓存中对象的函数；`destructor` 用于撤销这些操作（如果适用）。构造函数和析构函数接收一个 `size` 参数，以便它们可以支持相似缓存的家族（例如流消息）。`kmem_cache_create` 返回一个不透明的描述符，用于访问该缓存。

其次，由 (B) 可知，客户只需要两个简单的函数来分配和释放对象：

(2)

```c
void *kmem_cache_alloc(
struct kmem_cache *cp,
int flags);

```

从缓存中获取一个对象。该对象将处于已构造状态。`flags` 为 `KM_SLEEP` 或 `KM_NOSLEEP`，表示在当前没有可用内存时是否可以等待内存。

(3)

```c
void kmem_cache_free(
struct kmem_cache *cp,
void *buf);

```

将一个对象归还给缓存。该对象必须仍处于其已构造状态。

最后，如果不再需要某个缓存，客户可以将其销毁：

(4)

```c
void kmem_cache_destroy(
struct kmem_cache *cp);

```

销毁缓存并回收所有相关资源。所有已分配的对象必须已经归还给缓存。

该接口使我们能够构建一个理想地适应其客户需求的灵活分配器。从这个意义上说，它是一个“定制化”分配器。但是，它不需要像大多数定制分配器那样在编译时了解其客户 [Bozman84A, Grunwald93A, Margolin71]，也不需要像自适应匹配（adaptive-fit）方法那样持续进行推测 [Bozman84B, Leverett82, Oldehoeft85]。相反，对象缓存接口允许客户动态指定它们所需的分配服务。

### 2.4. 示例 (An Example)

本示例演示了针对 2.1 节中介绍的 ‘‘foo’’ 对象使用对象缓存的方法。

构造函数和析构函数例程如下：

```c
void
foo_constructor(void *buf, int size)
{
struct foo *foo = buf;
mutex_init(&foo->foo_lock, ...);
cv_init(&foo->foo_cv, ...);
foo->foo_refcnt = 0;
foo->foo_barlist = NULL;
}
void
foo_destructor(void *buf, int size)
{
struct foo *foo = buf;
ASSERT(foo->foo_barlist == NULL);
ASSERT(foo->foo_refcnt == 0);
cv_destroy(&foo->foo_cv);
mutex_destroy(&foo->foo_lock);
}

```

创建 foo 缓存：

```c
foo_cache = kmem_cache_create("foo_cache",
sizeof (struct foo), 0,
foo_constructor, foo_destructor);

```

分配、使用以及释放一个 foo 对象：

```c
foo = kmem_cache_alloc(foo_cache, KM_SLEEP);
use foo;
kmem_cache_free(foo_cache, foo);

```

这使得 `foo` 的分配变得非常快速，因为分配器通常只需从缓存中获取一个已经构造好的 `foo` 对象即可。`foo_constructor` 和 `foo_destructor` 将分别仅在填充和清空缓存时才被调用。

上面的示例展示了对象缓存的一个有益的副效应：通过将极少执行的构造和销毁代码移出热路径（hot path），它降低了使用缓存对象的代码在指令缓存（instruction-cache / I-Cache）中的占用足迹。

## 3. Slab 分配器的实现 (Slab Allocator Implementation)

本节将详细描述 SunOS 5.4 内核内存分配器（即“Slab 分配器”）的实现。（该名称来源于分配器的核心数据结构之一——Slab。这个名字在 Sun 公司内部沿用了下来，因为它比“object”或“cache”更具辨识度。Slab 将在 3.2 节中进行讨论。）

根据我们当下如何看待那块内存，术语 object（对象）、buffer（缓冲区）和 chunk（块）将或多或少地交替使用。

### 3.1. Caches

每个缓存都拥有前端（front end）和后端（back end），它们被设计得尽可能解耦：

```text
back end
kmem_cache_grow
kmem_cache_reap
      ▲
      │
      ▼
   cache
      ▲
      │
      ▼
front end
kmem_cache_alloc
kmem_cache_free

```

前端是分配器的公共接口。它将对象移入或移出缓存，当需要更多对象时便调用后端。

后端管理通过缓存的真实内存流。流入例程（`kmem_cache_grow()`）从虚拟内存（VM）系统获取内存，将其制作成对象，并将这些对象喂入缓存中。当 VM 系统想要收回部分内存时（例如在开始分页时），就会调用流出例程（`kmem_cache_reap()`）。请注意，所有后端活动完全由内存压力触发。当缓存需要更多对象时，内存就会流入；当系统的其余部分需要更多页时，内存就会流出；这里没有任意的限制或水位线（watermarks）。迟滞控制（Hysteresis control）由工作集算法提供，这将在 3.4 节中描述。

Slab 分配器并不是一个单体实体，而是一个由独立缓存组成的松散联邦。这些缓存之间没有共享状态，因此分配器可以使用**按缓存锁（per-cache locking）**，而不是用一个全局锁保护整个 arena（内核堆）。按缓存锁允许同时访问任意数量的不同缓存，从而提升了可扩展性。

每个缓存都维护着自己的统计信息——总分配量、已分配和空闲缓冲区的数量等。这些按缓存统计的信息为了解整体系统行为提供了洞察力。它们指示了系统的哪些部分消耗了最多的内存，并有助于识别内存泄漏。在分配器流量能够准确近似的范围内，它们还指示了各个子系统的活动水平（例如，流消息分配直接衡量了流的活动度）。

Slab 分配器在操作上类似于“CustoMalloc”[Grunwald93A]、“QuickFit”[Weinstock88] 和“Zone”[VanSciver88] 分配器，所有这些分配器都为最常请求的缓冲区大小维护着独立的空闲链表（freelists）。Grunwald 和 Weinstock 的论文各自证明，一个定制的隔离存储（segregated-storage）分配器——即先验地了解最常见分配大小的分配器——通常在时间和空间效率上都是最优的。Slab 分配器就属于这一类，但其优势在于它的定制化是在运行时由客户驱动的，而不是在编译时硬编码的（Zone 分配器也是如此）。

标准的无缓存分配例程 `kmem_alloc(9F)` 和 `kmem_free(9F)` 在内部使用对象缓存。在系统启动时，系统会创建一组大约 30 个缓存，大小从 8 字节到 9K 不等，增幅约为 10-20%。`kmem_alloc()` 只是简单地从最接近其大小的缓存中执行一次 `kmem_cache_alloc()`。大于 9K 的分配非常罕见，将直接由后端页提供者处理。

### 3.2. Slabs

Slab 是 Slab 分配器中的基本通用单位。例如，当分配器需要扩容某个缓存时，它会一次性获取一整块包含多个对象的 Slab。同样地，分配器通过释放一整个 Slab 来回收未使用的内存（对缓存进行缩容）。

一个 Slab 由一页或多页在虚拟内存上连续的页组成，这些页被分割成若干大小相同的块（chunks），并配有一个引用计数（reference count），用以指示其中有多少个块已经被分配出去。使用这种简单的数据结构来管理内核堆（arena）所带来的收益相当显著：

(1) **回收未使用内存极为简单。** 当 Slab 的引用计数变为零时，相关联的内存页就可以直接归还给虚拟内存（VM）系统。因此，一个简单的引用计数就替代了大多数其他分配器中常见的复杂树结构、位图以及合并算法 [Knuth68, Korn85, Standish80]。

(2) **分配与释放内存是快速的常数时间（$O(1)$）操作。** 我们所要做的全部工作，就是将一个对象移入或移出空闲链表（freelist），并更新引用计数。

(3) **极难发生严重的外部碎片（即空闲链表上存在大量无法利用的缓冲区）。** 随着时间的推移，许多分配器会逐渐累积大量细小且无法利用的缓冲区。这是由于分配器通过拆分现有的空闲缓冲区来满足较小的分配请求所致。例如，一连串 32 字节和 40 字节的分配请求序列，最终可能会导致大量 8 字节空闲缓冲区的累积——即使系统从未请求过 8 字节的缓冲区 [Standish80]。隔离存储（segregated storage）分配器不会遭受这种命运，因为填充其 8 字节空闲链表的唯一方式，就是实际去分配和释放 8 字节的缓冲区。任何 32 字节和 40 字节的分配请求序列——无论多么复杂——都只会导致 32 字节和 40 字节空闲链表被填充。由于先前的分配是预测未来分配的良好指标 [Weinstock88]，这些缓冲区极有可能被再次使用。

Slab 能够减少外部碎片的另一个原因在于，同一个 Slab 中的所有对象都属于相同类型，因此它们具有相同的生命周期分布*。这种在 Slab 粒度上对短生命周期对象与长生命周期对象进行的隔离，降低了整个物理页因为单个长生命周期对象的分配而被“绑架”（无法释放）的概率 [Barrett93, Hanson90]。

---

## * 支持 `kmem_alloc()` 的通用缓存是一个显著的特例，但在 SunOS 5.4 中，它们占内核堆的比例相对较小——所有主要的内存消耗者现在都使用 `kmem_cache_alloc()`。

(4) **内部碎片（每个缓冲区内浪费的空间）极小。** 每个缓冲区的大小都恰好合适（即缓存的对象大小），因此唯一被浪费的空间就是 Slab 末尾未使用的部分。例如，假设采用 4096 字节的页，一个 400 字节对象缓存中的 Slab 每个将包含 10 个缓冲区，剩余 96 字节。我们可以将这视为每个 400 字节缓冲区相当于浪费了 9.6 字节的空间，或者说存在 2.4% 的内部碎片。

一般而言，如果一个 Slab 包含 $n$ 个缓冲区，那么内部碎片最多为 $1/n$；因此分配器实际上可以通过控制 Slab 的大小来控制内部碎片的数量。然而，较大的 Slab 更容易引起外部碎片，因为随着每个 Slab 中缓冲区数量的增加，能够回收整个 Slab 的概率就会降低。SunOS 5.4 的实现将内部碎片限制在 12.5%（$1/8$），因为经验表明这是内部碎片与外部碎片权衡之间的最佳平衡点（sweet-spot）。

#### 3.2.1. Slab 布局 —— 逻辑布局

每个 Slab 的内容由一个 `kmem_slab` 数据结构进行管理，该结构维护了 Slab 在缓存中的链表连接、其引用计数以及它的空闲缓冲区链表。反过来，Slab 中的每个缓冲区由一个 `kmem_bufctl` 结构进行管理，该结构保存了空闲链表连接、缓冲区地址以及指向控制 Slab 的反向指针。从图形上看，一个 Slab 如下所示（未展示 bufctl 到 slab 的反向指针）：

```text
prev slab in cache
kmem
slab
next slab in cache

kmem
bufctl

kmem
bufctl

buf

buf

kmem
bufctl

buf

un
used

one or more pages

```

#### 3.2.2. 小对象的 Slab 布局

对于小于 $1/8$ 页的对象，Slab 的构建方式是分配一个页，将 Slab 的管理数据放在末尾，并将其余部分分割成大小相等的缓冲区：

```text
buf

buf

...

buf

buf

un
used

kmem
slab

one page

```

每个缓冲区在空闲链表上时充当其自身的 `bufctl`。由于其他所有信息都是可计算的，因此实际上只需要链表连接。这些对于小缓冲区来说是至关重要的优化——否则我们最终为 `bufctl` 分配的内存几乎会和为缓冲区本身分配的内存一样多。

空闲链表连接放置在缓冲区的末尾而不是开头，以方便调试。这是由经验观察所驱动的：数据结构的开头通常比末尾更加活跃。如果一个缓冲区在被释放后被错误修改（例如野指针踩内存），如果堆结构（空闲链表连接）仍然完好，问题将更容易被诊断。分配器会为已构造的对象保留一个额外字（word）的空间，以便链表连接不会覆盖任何已构造的状态。

#### 3.2.3. 大对象的 Slab 布局

上述方案对小对象很高效，但对大对象则不然。由于嵌入了 Slab 管理数据，它在一个 4K 的页上只能塞下一个 2K 的缓冲区。此外，对于大型（多页）Slab，我们失去了从缓冲区地址推算 Slab 数据地址的能力。因此，对于大对象，其物理布局与逻辑布局完全相同。所需的 `kmem_slab` 和 `kmem_bufctl` 数据结构来自它们自己的（小对象！）缓存。一个按缓存配置的自扩展哈希表提供了从“缓冲区”到“`bufctl`”的转换。

### 3.3. 空闲链表管理 (Freelist Management)

每个缓存都维护着一个由其所有 Slab 组成的双向循环链表。Slab 链表是部分排序的：空 Slab（所有缓冲区均已分配）排在最前面，其次是部分空闲 Slab（部分缓冲区已分配，部分空闲），最后是完全空闲 Slab（所有缓冲区均空闲，`refcnt == 0`）。缓存的空闲链表指针指向其第一个非空 Slab。反过来，每个 Slab 都有其自身的可用缓冲区空闲链表。这种两层空闲链表结构简化了内存回收。当分配器回收一个 Slab 时，它不必将每个缓冲区从缓存的空闲链表中逐个解链——它只需将该 Slab 本身解链即可。

### 3.4. 内存回收 (Reclaiming Memory)

当 `kmem_cache_free()` 察觉到 Slab 的引用计数变为零时，它不会立即回收该内存。相反，它只是将该 Slab 移动到空闲链表的末尾，也就是所有完全空闲 Slab 所在的区域。这确保了只要还有部分空闲 Slab 未被耗尽，就不会有任何完全空闲的 Slab 被拆散。

当系统内存不足时，它会请求分配器尽可能多地释放内存。分配器会配合执行，但会保留一个 15 秒的近期使用 Slab **工作集（working set）**，以防止内存抖动（thrashing）。测量表明，系统性能对 Slab 工作集的时间间隔相当不敏感。大概是因为两个极端——零工作集（按需回收所有完全空闲 Slab）和无限工作集（永远不回收任何东西）——都是合理但非最优的策略。

## 4. 硬件缓存效应 (Hardware Cache Effects)

现代硬件高度依赖于良好的缓存（Cache）利用率，因此在设计软件时考量缓存效应至关重要。对于一个内存分配器而言，需要考虑两大类缓存效应：缓冲区地址的分布，以及分配器本身的缓存足迹（cache footprint）。后者已经引起了一些关注 [Chen93, Grunwald93B]，但缓冲区地址分布对缓存利用率和总线平衡的影响在很大程度上尚未被充分认识。

### 4.1. 缓冲区地址分布对缓存利用率的影响

中等大小缓冲区的地址分布会影响系统的整体缓存利用率。特别是 **2 的幂次方分配器（power-of-two allocators）**——即所有缓冲区大小均为 $2^n$ 字节且按 $2^n$ 字节对齐——表现是最差的（pessimal）*。例如，假设每个 inode（约 300 字节）都被分配了一个 512 字节大小且 512 字节对齐的缓冲区，并且只有 inode 的前十几个字段（48 字节）被频繁引用。那么，大部分与 inode 相关的内存流量都将集中在模（modulo）512 处于 0 到 47 之间的地址上。因此，接近 512 字节边界的缓存行（cache lines）将被重度加载，而其余部分则处于闲置状态。实际上，inode 只能利用缓存的 9%（48/512）。全相联缓存（fully-associative caches）不会遭遇这个问题，但当前的硬件趋势是倾向于更简单而非更复杂的缓存结构。

---

## * 这类分配器很常见，因为它们很容易实现。例如，4.4BSD 和 SVr4 都采用了 2 的幂次方方法 [McKusick88, Lee89]。

当然，inode 并没有什么特殊之处。内核中还包含许多其他具有相同本质特征的中等大小数据结构（例如 100-500 字节）：它们数量众多，只包含少量被频繁使用的字段，且这些字段聚集在数据结构的开头或靠近开头的位置。这种由数据结构演变方式所产生的现象，此前在分配器设计中尚未被视作一个重要因素。

### 4.2. 缓冲区地址分布对总线平衡的影响

在跨多条主总线交叉并行（interleaves）内存的机器上，上述效应还会对总线利用率产生重大影响。例如，SPARCcenter 2000 在两条主总线之间采用了 256 字节交叉并行技术 [Cekleov92]。继续上面的例子，我们可以看到，任何 2 的幂次方分配器都会将每个 inode 的前半部分（热点部分）映射到总线 0，将后半部分映射到总线 1。因此，几乎所有与 inode 相关的缓存未命中（cache misses）都由总线 0 来响应。这种情况因膨胀的未命中率而进一步恶化，因为所有的 inode 都在争夺缓存中极小的一部分区域。

这些效应可能是极为剧烈的。在运行 SunOS 5.4 开发版内核且执行 LADDIS 测试的 SPARCcenter 2000 上，用 Slab 分配器替换旧的分配器（一种 2 的幂次方伙伴系统 [Lee89]）后，总线不平衡率从 43% 降至仅 17%。此外，一级缓存未命中率降低了 13%。

### 4.3. Slab 着色 (Slab Coloring)

Slab 分配器结合了一种简单的着色方案，将缓冲区均匀地分布在整个缓存中，从而实现了极佳的缓存利用率和总线平衡。这个概念很简单：每次创建一个新的 Slab 时，缓冲区的起始地址相较于 Slab 的基地址（该基地址总是页对齐的）都有一个微小的不同偏移量（即颜色）。例如，对于一个包含 200 字节对象且采用 8 字节对齐的缓存，第一个 Slab 的缓冲区相对于 Slab 基地址的偏移量分别为 0, 200, 400, ...。下一个 Slab 的缓冲区偏移量则为 8, 208, 408, ...，以此类推。最大的 Slab 颜色由 Slab 中未使用的空间量决定。在这个例子中，假设采用 4K 页面，我们可以在一个 4096 字节的 Slab 中塞下 20 个 200 字节的缓冲区。缓冲区消耗了 4000 字节，`kmem_slab` 数据消耗了 32 字节，剩下的 64 字节可用于着色。因此，最大的 Slab 颜色为 64，Slab 颜色序列为 0, 8, 16, 24, 32, 40, 48, 56, 64, 0, 8, ...

这种着色方案的一个特别优良的特性在于，中等大小的 2 的幂次方缓冲区获得了最大程度的着色，因为它们的空间拟合是最差的。例如，虽然 128 字节可以完美放入 4096 中，但放入 4096 - 32（即实际可用空间，因为嵌入了 Slab 数据）时却几乎是最差的拟合。

### 4.4. 堆区管理 (Arena Management)

分配器的堆区管理策略决定了其动态缓存足迹（dynamic cache footprint）。这些策略大致分为三类：顺序匹配法（sequential-fit）、伙伴法（buddy methods）和隔离存储法（segregated-storage methods）[Standish80]。

顺序匹配分配器通常必须搜索多个节点才能找到合适大小的缓冲区。这类方法天然地注定了具有较大的缓存足迹：它们不得不检查相当数量的节点，而这些节点在内存中通常相距甚远。这不仅会导致缓存未命中，还会导致 TLB 未命中。伙伴系统分配器的合并阶段 [Knuth68, Lee89] 也具有类似的特性。

隔离存储分配器（如 Slab 分配器）为不同的缓冲区大小维护独立的空闲链表。这些分配器通常具有良好的缓存局部性，因为分配缓冲区非常简单。分配器所要做的全部工作就是确定正确的空闲链表（通过计算、通过表查找，或者作为参数直接提供），并从中取出一个缓冲区。释放缓冲区的过程同样简单。需要加载的指针屈指可数，因此缓存足迹很小。

Slab 分配器还有一个额外的优势：对于小到中等大小的缓冲区，绝大多数相关信息——Slab 数据、`bufctl` 结构以及缓冲区本身——都驻留在单个页面上。因此，单个 TLB 覆盖了绝大部分的执行动作。

## 5. 性能 (Performance)

本节将 Slab 分配器的性能与另外三种著名的内核内存分配器进行对比：

* **SunOS 4.1.3：** 基于 [Stephenson83]，一种顺序匹配法（sequential-fit method）；
* **4.4BSD：** 基于 [McKusick88]，一种 2 的幂次方隔离存储法（power-of-two segregated-storage method）；
* **SVr4：** 基于 [Lee89]，一种 2 的幂次方伙伴系统法（power-of-two buddy-system method）。该分配器曾用于此前所有的 SunOS 5.x 版本中。

为了获得公平的对比，每种分配器都被移植到了相同的 SunOS 5.4 基础系统中。这确保了我们比较的仅仅是分配器本身，而不是整个操作系统。

### 5.1. 速度对比 (Speed Comparison)

在 SPARCstation-2 上，各种分配器下分配和释放一个缓冲区所需的时间如下：

| Allocator | Time (μsec) | Interface |
| --- | --- | --- |
| **slab** | 3.8 | `kmem_cache_alloc` |
| **4.4BSD** | 4.1 | `kmem_alloc` |
| **slab** | 4.7 | `kmem_alloc` |
| **SVr4** | 9.4 | `kmem_alloc` |
| **SunOS 4.1.3** | 25.0 | `kmem_alloc` |

**注：** 4.4BSD 分配器同时提供了函数接口和预处理器宏接口。这些测量针对的是函数版本。通常不考虑非二进制接口，因为这些接口在不暴露实现的情况下无法导出给驱动程序。4.4BSD 分配器在编译时未定义 `KMEMSTATS`（默认开启），以获取最快的代码。

一对 `mutex_enter()/mutex_exit()` 的开销为 1.0 微秒，因此分配和释放一个缓冲区所需的锁开销构成了 2.0 微秒的下限。Slab 和 4.4BSD 分配器都非常接近这个极限，因为它们在常见情况下做的工作很少。4.4BSD 的 `kmem_alloc()` 实现稍微快一些，因为它的统计账务工作更少（它从不回收内存）。

然而，Slab 分配器的 `kmem_cache_alloc()` 接口甚至更快，因为它不必确定使用哪个空闲链表（缓存）——缓存描述符是作为参数传递给 `kmem_cache_alloc()` 的。无论如何，Slab 和 4.4BSD 分配器之间的速度差异很小。这是意料之中的，因为所有隔离存储方法在操作上都是相似的。任何优秀的隔离存储实现都应该能达到极佳的性能。

SVr4 分配器比大多数伙伴系统慢，但仍能提供合理、可预测的速度。SunOS 4.1.3 分配器像大多数顺序匹配方法一样，相对较慢且波动很大。

对象缓存的好处在上面的数字中不可见，因为它们只测量了分配器本身的开销。下表展示了对象缓存对 SunOS 5.4 内核中一些最频繁分配的影响（SPARCstation-2 计时，单位微秒）：

| Allocation Type | Without Caching | With Caching | Improvement |
| --- | --- | --- | --- |
| **allocb** | 8.3 | 6.0 | 1.4x |
| **dupb** | 13.4 | 8.7 | 1.5x |
| **shalloc** | 29.3 | 5.7 | 5.1x |
| **allocq** | 40.0 | 10.9 | 3.7x |
| **anonmap_alloc** | 16.3 | 10.1 | 1.6x |
| **makepipe** | 126.0 | 98.0 | 1.3x |

本节中展示的所有数字都单项测量了分配器的性能。分配器对系统整体性能的影响将在 5.3 节中讨论。

### 5.2. 内存利用率对比 (Memory Utilization Comparison)

分配器消耗的内存通常多于客户实际请求的内存，原因在于不完美的拟合（内部碎片）、空闲链表上未使用的缓冲区（外部碎片），以及分配器内部数据结构的开销。请求的内存与消耗的内存之比即为分配器的**内存利用率（memory utilization）**。互补的比例则是内存浪费（memory wastage）或总碎片率。良好的内存利用率至关重要，因为内核堆消耗的是物理内存。

分配器的空间效率比其速度更难表征，因为它依赖于工作负载。我们能做的最好尝试，就是在固定的一套工作负载下测量各种分配器的内存利用率。为此，每种分配器都承受了以下工作负载序列：

(1) **System boot（系统启动）：** 这测量了重启后在控制台登录提示符下的系统内存利用率。

(2) **A brief spike in load（短暂的负载突发）：** 由以下简单程序生成：

```c
fork(); fork(); fork(); fork();
fork(); fork(); fork(); fork();
fd = socket(AF_UNIX, SOCK_STREAM, 0);
sleep(60);
close(fd);

```

这创建了 256 个进程，每个进程创建一个套接字。这导致对各种内核数据结构的需求暂时激增。

(3) **Find：** 这是另一个简单的突发生成器：

```sh
find /usr -mount -exec file {} \;

```

(4) **Kenbus：** 这是一个标准的分时（timesharing）基准测试。Kenbus 产生了大量的并发活动，对用户和内核内存都创造了巨大需求。

在每一步之后都测量了内存利用率。下表总结了一台 16MB SPARCstation-1 的结果。Slab 分配器的表现明显优于其他分配器，最终的碎片率只有最接近的竞争对手的一半（结果是累积的，因此 “kenbus” 列指示了完成所有四个步骤后的碎片率）：

| Allocator | Boot | Spike | Find | Kenbus | s/m |
| --- | --- | --- | --- | --- | --- |
| **slab** | 11% | 13% | 14% | 14% | 233 |
| **SunOS 4.1.3** | 7% | 19% | 19% | 27% | 210 |
| **4.4BSD** | 20% | 43% | 43% | 45% | 205 |
| **SVr4** | 23% | 45% | 45% | 46% | 199 |

最后一列展示了 kenbus 的结果，它以每分钟执行的脚本数（s/m）为单位测量峰值吞吐量。在这台 16MB 的系统上，Kenbus 的性能主要受限于内存，这就是为什么 SunOS 4.1.3 分配器尽管速度明显更慢，却取得了比 4.4BSD 分配器更好的结果。Slab 分配器以 11% 的优势提供了最佳性能，因为它既快速又具备高空间效率。

为了掌握真实生活中的性能，作者在他个人的桌面机器（一台 32MB 的 SPARCstation-2）上将这些分配器中的每一种都使用了一周。这台机器主要用于阅读电子邮件、运行简单命令和脚本，以及连接到测试机器和计算服务器。这个显然非对照实验的结果为：

| Allocator | Kernel Heap | Fragmentation |
| --- | --- | --- |
| **slab** | 6.0 MB | 9% |
| **SunOS 4.1.3** | 6.7 MB | 17% |
| **SVr4** | 8.5 MB | 35% |
| **4.4BSD** | 9.0 MB | 38% |

这些数字与上面描述的合成工作负载的结果是一致的。在这两种情况下，Slab 分配器产生的碎片大约是 SunOS 4.1.3 的一半，而 SunOS 4.1.3 产生的碎片大约是 SVr4 和 4.4BSD 的一半。

### 5.3. 系统整体性能 (Overall System Performance)

内核内存分配器以多种方式影响系统整体性能。在前几节中，我们考量了若干单独因素的影响：对象缓存、硬件缓存与总线效应、速度以及内存利用率。我们现在转向最重要的指标：有价值的工作负载的最终性能。在 SunOS 5.4 中，基于 SVr4 的分配器被这里描述的 Slab 分配器所取代。下表展示了在几个关键领域的净性能提升。

| Workload | Gain | What It Measures |
| --- | --- | --- |
| **DeskBench** | 12% | 窗口系统 |
| **kenbus** | 17% | 分时系统 |
| **TPC-B** | 4% | 数据库 |
| **LADDIS** | 3% | NFS 服务 |
| **parallel make** | 5% | 并行编译 |
| **terminal server** | 5% | 多用户打字 |

**注：**
(1) DeskBench 和 kenbus 在 16MB 内存下都受内存限制，因此这里的大部分提升归功于 Slab 分配器的空间效率。
(2) TPC-B 工作负载产生的内核内存分配极少，因此分配器的速度在这里不是显著因素。该测试在一台拥有足够内存的巨型服务器上运行，它从未发生过分页（在任何一种分配器下），因此空间效率也不是因素。4% 的性能提升完全归功于更好的缓存利用率（一级缓存未命中减少 5%，二级缓存未命中减少 2%）。
(3) Parallel make（并行编译）在一台从未发生分页的巨型服务器上运行。该工作负载产生了大量的分配器流量，因此这里的提升归因于 Slab 分配器的速度、对象缓存以及系统整体较低的缓存未命中率（一级缓存未命中减少 5%，二级缓存未命中减少 4%）。
(4) Terminal server（终端服务器）也在一台从未发生分页的巨型服务器上运行。使用旧分配器时，该基准测试在内核中花费了 25% 的时间，而使用新分配器时则为 20%。因此，5% 的最终提升归因于内核时间减少了 20%。

## 6. 调试功能 (Debugging Features)

损坏内核堆的编程错误——例如修改已释放的内存、重复释放缓冲区、释放未初始化的指针或写入超出缓冲区末尾——通常很难调试。幸运的是，一个配备了完善仪器（instrumented）的内核内存分配器可以检测出许多此类问题。

本节描述 Slab 分配器的调试功能。这些功能可以通过在 `kadb`（内核调试器）下引导并设置相应的标志，在任何 SunOS 5.4 内核中启用（不仅限于特殊的调试版本）*。当分配器检测到问题时，它会在系统控制台上提供详细的诊断信息。

---

## * 这些调试功能的可获得性不会增加大多数分配的开销。表示是否存在哈希表（即缓存的对象是否大于 $1/8$ 页）的按缓存标志字中，也包含了调试标志。单个测试可同时检查所有这些标志，因此常见情况（小对象、无调试）不受影响。

### 6.1. 审计 (Auditing)

在审计模式下，分配器会在一个循环事务日志中记录其活动。它将这些信息存储在 `bufctl` 结构的扩展版本中，其中包括线程指针、高精度时间戳和事务的堆栈追踪（stack trace）。当通过任何其他方法检测到损坏时，可以确定受影响缓冲区的先前拥有者（可能的嫌疑对象）。

### 6.2. 已释放地址验证 (Freed-Address Verification)

大对象缓存所采用的“缓冲区到 `bufctl`”哈希表可以用作调试功能：如果在 `kmem_cache_free()` 中的哈希查找失败，那么调用者一定是在尝试释放一个伪造的地址。分配器可以通过将“大对象”阈值更改为零，来验证所有被释放的地址。

### 6.3. 检测已释放内存的使用 (Detecting Use of Freed Memory)

当一个对象被释放时，分配器会应用其析构函数，并填充模式 `0xdeadbeef`。下一次分配该对象时，分配器会验证它是否仍包含 `deadbeef` 模式。然后它用 `0xbaddcafe` 填充该对象并应用其构造函数。选择 `deadbeef` 和 `baddcafe` 模式是为了在调试会话中易于被人识别。它们分别代表已释放的内存和未初始化的数据。

### 6.4. 红区检查 (Redzone Checking)

红区检查用于检测越过缓冲区末尾的写入（缓冲区溢出）。分配器通过在每个缓冲区的末尾添加一个保护字（guard word），并在释放缓冲区时验证其未被修改，来检查红区违规情况。

### 6.5. 同步解映射 (Synchronous Unmapping)

通常，Slab 工作集算法会保留完全空闲的 Slab 一段时间。在同步解映射模式下，分配器会立即销毁完全空闲的 Slab。`kmem_slab_destroy()` 将底层内存归还给后端页提供者，由后者解映射（unmap）这些页面。随后对该 Slab 中任何对象的任何引用都会引发内核数据故障（kernel data fault）。

### 6.6. 单缓冲区一页模式 (Page-per-buffer Mode)

在单缓冲区一页模式下，每个缓冲区都被赋予一整页（或多页），以便在释放时解映射每个缓冲区。Slab 分配器通过将所有缓存的对齐方式提高到系统页面大小来实现这一点。（此功能需要极其庞大的物理内存。）

### 6.7. 泄漏检测 (Leak Detection)

审计提供的时间戳使得在用户层实现一个简易的内核内存泄漏检测器变得容易。用户层程序所要做的就是定期扫描堆区（通过 `/dev/kmem`），寻找新的、长期存在的分配。例如，一个在 1 小时前分配且现在仍然处于分配状态的缓冲区可能就是一次泄漏。

## 7. 未来方向 (Future Directions)

### 7.1. 管理其他类型的内存 (Managing Other Types of Memory)

Slab 分配器通过 `kmem_getpages()` 和 `kmem_freepages()` 例程从 `segkmem` 获取其页面；它不对底层的段驱动程序（segment driver）、资源映射、转换设置等做任何假设。由于分配器遵守了这个防火墙，插入替代的后端页提供者将是非常简单的。`getpages` 和 `freepages` 例程可以作为额外的参数传递给 `kmem_cache_create()`。这将允许我们用单个分配器管理多种类型的内存（例如普通内核内存、设备内存、可分页内核内存、NVRAM 等）。

### 7.2. 按处理器内存分配 (Per-Processor Memory Allocation)

McKenney 和 Slingwine [McKenney93] 的按处理器分配技术可以很好地叠在 Slab 分配器之上。他们定义了一个由四层组成的分配层级结构，速度和局部性依次递减：按 CPU（per-CPU）、全局（global）、合并至页（coalesce-to-page）和合并至 VM 块（coalesce-to-VM-block）。后三层分别与 Slab 分配器的前端、后端和页提供者层密切对应。即使在没有锁争用的情况下，小的按处理器空闲链表也可以通过消除锁开销和减少失效流量（invalidation traffic）来提高性能。

### 7.3. 用户级应用程序 (User-level Applications)

Slab 分配器也可以用作用户级内存分配器。后端页提供者可以是 `mmap(2)` 或 `sbrk(2)`。

## 8. 结论 (Conclusions)

Slab 分配器是一个简单、快速且高空间效率的内核内存分配器。它所基于的对象缓存接口降低了分配和释放复杂对象的开销，并使分配器能够按大小和生命周期分布隔离对象。Slab 利用对象大小和生命周期的隔离，分别减少了内部和外部碎片。Slab 还通过使用简单的引用计数代替合并操作来简化回收过程。Slab 分配器在其客户与 VM 系统之间建立了一种推/拉（push/pull）关系，消除了对用于控制回收的任意限制或水位线的需求。分配器的着色方案在整个缓存中均匀地分布缓冲区，改善了系统的整体缓存利用率和总线平衡。在几个重要领域，Slab 分配器提供了可衡量的、更好的系统性能。
